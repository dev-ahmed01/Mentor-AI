# Personalized Roadmaps Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Turn the selected career's learning priorities into a saved, editable roadmap.

**Architecture:** Add a roadmap aggregate with phases, skill tasks and prerequisite
snapshots. Deterministic generation topologically orders decision candidates;
reads derive next action and a bounded weekly focus. Next.js exposes authenticated
generation and editing through Server Actions. Existing scoring remains unchanged.

**Tech Stack:** Java 25, Spring Boot/JPA, Flyway/PostgreSQL, Next.js 16, React 19.

**Spec:** `docs/MentorAI_Hackathon_Phases_and_Codex_Prompt.md`, Phase 3.

## Contracts and policy

- POST `/api/roadmaps` accepts careerId and requires recorded weekly time.
- GET `/api/roadmaps/current` returns the latest created roadmap (404 if none).
- GET `/api/roadmaps/{id}` and PUT `/api/roadmaps/{id}` enforce authenticated
  ownership; other users receive 404. PUT requires expectedRevision and supports
  an optional roadmap title plus bounded task edits (title, estimatedHours, state).
- Each generation is a new saved snapshot; older roadmaps remain readable by ID.
  A previousRoadmapId link connects sequential generations. No delete API.
- V4 creates roadmaps, roadmap_phases, roadmap_tasks and task prerequisite
  snapshots. Foreign keys, per-parent positions, states and effort bounds are
  constrained. Roadmap @Version plus an updatedAt touch protects child edits.
- Candidates and scores come from learning-priorities-v1. Repeatedly select the
  highest scoring candidate whose prerequisite candidates have been emitted;
  use name/UUID ties. Include already-known targets as SKIPPED, explicitly marked
  as satisfied at generation. Only the selected career and its foundations appear.
- Group the ordered tasks into phases of at most three. Phases are learning
  stages, not calendar weeks. Current phase is the first with unfinished work.
- Starter effort is 8 hours for building foundations, 4 for developing basics,
  zero for already-met targets. All are editable DEMO estimates, not validated
  mastery times. Completion is self-reported and never writes profile proficiency.
- Snapshot each prerequisite's satisfaction at generation. A prerequisite is
  ready when that snapshot is satisfied or its roadmap task is COMPLETED.
  A user-skipped unknown foundation does not unlock downstream tasks.
- State transitions: NOT_STARTED -> IN_PROGRESS/COMPLETED/SKIPPED/NEEDS_REVIEW;
  IN_PROGRESS -> NOT_STARTED/COMPLETED/SKIPPED/NEEDS_REVIEW;
  COMPLETED -> NEEDS_REVIEW; SKIPPED -> NOT_STARTED/NEEDS_REVIEW;
  NEEDS_REVIEW -> NOT_STARTED/IN_PROGRESS/COMPLETED/SKIPPED. Same state permits edits.
  Starting/completing a task requires satisfied prerequisites. Batch edits validate
  the proposed aggregate atomically, not request order. Invalid or stale edits
  leave all tasks unchanged. Active tasks require a positive effort estimate.
- This week allocates at most saved weeklyHours and Phase 2's focus limit among
  ready unfinished tasks in roadmap order, with IN_PROGRESS work first. A task
  larger than capacity gets a partial focus allocation; no automatic completion.
- Later and blocked work is collapsed by default. Show current phase, next action,
  This week, later phases, completed/skipped state, and why this order.
- No AI, automatic regeneration, progress check-ins, calendar scheduling or
  adaptive revisions in this phase. Those belong to later phases.
